## Work units

Let $n$ be the array size, $w=r-l+1$ the width of a nonempty query, $h=\lceil\log_2 n\rceil$ the padded segment-tree height, $Q$ the number of queries, $U$ the number of assignments, and $V$ the maximum calibration value. Count reads $R$, writes $W$, combines $C$, rebuilt cells $B$, and Euclid divisions $E$ separately. A candidate time model is

$$
T=\alpha+\beta_R R+\beta_W W+\beta_C C+\beta_B B+\beta_E E+\epsilon.
$$

The coefficients are machine- and implementation-specific. The counters can overlap in meaning, so the model alone does not identify separate coefficients from a timing. The main predictions concern scaling in work units.

## Indexed structures

**Max-count segment tree.** The padded complete tree has fewer than $4n$ slots for $n>1$, so filling its leaves and combining once per internal node takes $O(n)$. An assignment replaces one leaf and follows its unique path to the root, rebuilding exactly $h$ ancestors. A nonempty range has at most two boundary contributions at each level, so both max-only and max-count queries inspect $O(h+1)$ summaries. Returning the maximum projects the same aggregate used by the count query.

**GCD segment tree.** The representation and number of combines are the same. Within a query accumulator, each positive running GCD $g_j$ divides the previous one. The Euclid call costs $O(1+\log(g_{j-1}/g_j))$ because the remainder falls geometrically after an initial step at each call. Summing the ratios in log form gives $\log(g_0/g_k)\le\log V$. Handle zeros in constant work and charge the final merge another $O(\log V)$. Thus the query costs $O(h+1+\log(V+1))$, while construction and assignments have the segment tree's combine counts with additional data-dependent Euclid work. See D3 for the detailed argument.

**Two-tree Fenwick maximum.** Each endpoint walk clears its least significant set bit or moves to an ancestor with a larger lowbit. It therefore consumes $O(\log n+1)$ blocks before the two paths meet. The two arrays build with linear passes. For a point assignment, count the ancestors rebuilt on the two paths and separately count the neighbor blocks read to repair them. An analysis of the specific repair loop is necessary to translate the ancestor count into a bound on total reads.

## Prefix Fenwick and oracle

**Prefix-max Fenwick.** Prefix $r$ decomposes into $\operatorname{popcount}(r)$ saved cells. Build propagates each cell to at most one parent, so it is linear. An increase touches $O(\log n+1)$ update-path cells. For a decrease, let $J$ be the set of stale cells and $\operatorname{lowbit}(j)$ the width of cell $j$. With a full rescan per stale block, the extra reads and combines total $S=\sum_{j\in J}\operatorname{lowbit}(j)$, and the rebuilt-cell count is $|J|$. Widths at least double as the path rises, giving $S<2n$. For $n$ a power of two, repeatedly lowering the unique maximum at index 1 after restoring it reaches all powers-of-two endpoints. Each lowering rescans $1+2+\cdots+n=2n-1$ values. This explains how logarithmically many rebuilt cells can require linear work.

**Plain array.** Build copies $n$ values. An assignment writes one entry. A query scans exactly $w$ elements, or $r$ for a prefix. For GCD the scan has $w$ combines and a value-dependent number of Euclid steps. The same running-GCD argument bounds the total as $O(w+\log(V+1))$ for a nonempty range.

## Predictions at the required scale

| Workload | Predicted work |
| --- | --- |
| $n=1{,}000{,}000$, one million segment-tree assignments | $h=20$, so 20,000,000 ancestors rebuilt |
| A million maximum queries at width 1 | The array inspects 1,000,000 values |
| A million maximum queries at width 64 | The array inspects 64,000,000 values |
| A million maximum queries at full width | The array inspects $10^{12}$ values |
| Wide maximum queries as $n$ grows | Average work depends on alignment. Both indexed designs have logarithmic query bounds. |
| Prefix decreases at $n=32{,}768$, hot index 1 | A full rescan rebuilds 16 cells and inspects 65,535 values per lowering |

A scan can be competitive at very short widths. Its per-element term grows with $w$, so the crossover depends on implementation constants and the machine. Indexed query speed also depends on which blocks the endpoints select. Block counts and timings must be compared on the same trace.
